# Evaluation reports

Six reports, all generated by `scripts/run_eval.py` from cached run files with
**zero API calls**. Superseded reports are kept deliberately: a directory that
holds only the flattering run is a sales document, not a record.

Two of them back every number published in the README and the deck.

| Report | Rows | Model | Prompt | Type accuracy | Status |
|---|---|---|---|---|---|
| `corpus_test70_v2` | 100 | 70B | v1 | **88.0%** | **Headline.** Held-out split, executed once, single-tier provenance verified before any accuracy was computed. |
| `holdout70_v2` | 40 | 70B | v1 | **92.5%** | **Headline.** Cross-family holdout, generated by Gemini. Model-only 97.5%. |
| `corpus_dev70_v1_strat` | 60 | 70B | v1 | 85.0% | Stratified dev slice. The 70B calibration figure (ECE 0.063) quoted in `workflows.yaml` comes from here. |
| `corpus_dev70_v1` | 60 | 70B | v1 | 85.0% | First 70B transfer check. Pooled with the stratified slice by `scripts/diag/pool_70b.py` to derive the per-class gates. |
| `corpus_dev_bulk` | 200 | 8B | v1 | 70.5% | The prompt-v1 development batch. The ensemble gate on the bulk tier was derived here. |
| `corpus_dev_bulk_v2` | 200 | 8B | v2 | 71.0% | **Superseded.** Prompt v2, reverted — fractionally ahead on aggregate accuracy and worse at every operating point. See DECISIONS #7. |

## Reading these

**The `_v2` in a filename is the run iteration, not the prompt version.** The
prompt version is recorded inside every row and on the report header. Both
headline runs read `prompt versions: v1`, because v2 was measured and reverted.

**`- configured threshold:` in the Gate status section is a CLI default, not the
system's gate.** `run_eval.py --threshold` defaults to 0.72 and exists so the
report can flag an inert gate. Live gating reads `auto_policies` in
`triage/workflows.yaml` and is per-class. A report printing `0.72` is describing
the diagnostic, not the system.

**Operating-point tables are sweeps over the split being reported.** They answer
"what precision is available at what volume on this data", which is not the same
question as "what does the shipped config do". The shipped policy is
`billing_dispute >= 0.90` on the quality tier and a floor-agreement ensemble on
the bulk tier.

**Only two runs are reproducible from a clean clone.** `.gitignore` keeps four
`.jsonl` files and drops every `.db`, so the two commands in the README's setup
section work and the dev-70B and prompt-v2 reports cannot be regenerated without
re-running the batch. Their `.md` and `.json` outputs are committed as the
record.

## Regenerating the two headline reports

```bash
python3 scripts/run_eval.py --run corpus_test70_v2 --floor corpus_test_floor --write
python3 scripts/run_eval.py --run holdout70_v2 --write
```

No API key required. `--write` refreshes the `.md` and `.json` in this directory.
